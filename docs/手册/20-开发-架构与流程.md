# 20 · 开发者篇 · 架构与流程

面向二次开发者：解释问题模块的 **Define→compile→Manager** 组织、优化器的**执行链**、以及从配置到运行的**装配流程**。
（新增算子的具体步骤见 [21-开发-内部组件](21-开发-内部组件.md)。）

---

## 1. 问题模块：4 域 × Define/Manager

原单体 `Problem` 被**横向切成 4 域**（Variable/Objective/Constrain/Heuristic），每域**纵向分两态**：

```
        定义态(描述)              编译产物(运行期引擎)
Problem ├─ VariableDefine  ─┐
        ├─ ObjectiveDefine  │  compile()   ┌─ VariableManager  ─┐
        ├─ ConstrainDefine  ├────────────► │  ObjectiveManager  ├─► ProblemHandle
        └─ HeuristicDefine ─┘              │  ConstrainManager  │   (+ 跨域编排)
                                           └─ HeuristicManager ─┘
```

- **`XXDefine`**（`problem/define/*.h`）：域的**描述切片**——`add*` 方法把用户输入填进去，无运行期状态。`Problem` 持有 4 个 Define，`Problem::add*` 委派给对应 Define。
- **`XXManager`**（`problem/manager/*.h`）：`XXDefine::compile()` 的**产物**——编译后的域运行期引擎（布局固化 + 域内操作）。
- **`Problem::compile()`**：把 4 个 Define 各自 `compile()` 成 Manager，组装进 `ProblemHandle`。
- **`ProblemHandle`**（`problem/core/problem-handle.h`）：持 4 个 Manager + **跨域编排**（`solutionEvaluate` 需目标读变量+约束罚、`getPrioriChoice` 需约束域+启发域协同…）。**优化器只见 ProblemHandle**，不碰 Define/Manager。

> 设计意图：定义（用户描述）与运行（求解引擎）分离；4 域单一职责、可独立演进；`compile()` 是唯一的"描述→引擎"转换点。约束族实现在 `problem/constrain/`（域/基数/累积/图/cp 表达式），启发在 `problem/heuristic/`。

## 2. 优化器模块：执行单元层级

```
Optimizer ──持──► Population(顶层聚合,旧 Swarm) ──持──► SubpopulationManager
                                                          │ 统辖 N 个
                                                          ▼
                                              Subpopulation(子种群) ──持──► O_Workflow
                                                          │                    │ 每代顺跑
                                              IndividualArray(个体集)          ▼
                                                          │            [O_Component 流水线]
                                              Individual(个体,+挂载特性)
```

- **`Individual`**：唯一基本单元，持一个 `Solution` + 一个**特性袋**（velocity/pbest/sigma/… 经组件 `featureDemands()` 装配期推断挂载；无子类）见 [21](21-开发-内部组件.md)。
- **`IndividualArray`**：个体集（容量/大小分离，类 vector）。
- **`Subpopulation`**：子种群——生成+选择的**基本单元**，持一条 `O_Workflow`。
- **`SubpopulationManager`**：定义子群交互方式、并驱动构建器/拓扑（迁移/重聚类/无交互/单群）。注册 tag：`Single`/`NoInteraction`/`Immigrant`/`RebuildTopology`。v1.4.8 模板方法化：`runEpoch` 固定时序 + 唯一钩子 `interact()`，终止器两级预算记账由框架包办。
- **`Population`**：顶层聚合（薄壳，委派管理器）+ 全局最优档案。
- **`Optimizer`**：顶层，持 Population + Terminator + Logger + `ProblemHandle` 副本；`exe(seed)` / `exe(n,seed)` 驱动。

## 3. 执行链：一代内发生什么

`Subpopulation` 的 `O_Workflow` 持**一张有序的 `O_Component` 表**（按配置顺序），每代顺跑：

```
每代:
  ┌ RunGenerate  : topology.getTopology(种群)→学习图; 逐起点 strategy 生成子代; repair 修复
  │                 (offspring 追加,不清空)
  ├ RunGenerate  : (可有多段,如 GA 交叉段+变异段;段间 offspring 累积)
  ├ RunEvaluate  : evaluator 逐子代 solutionEvaluate; 更新 archive; terminator FES++
  └ RunSelect    : selector.update_subswarm(parent, offspring) → 新一代; 然后 offspring.clear()
```

- **`O_Component`**（`orchestrate/optimize-component.h`）：流水线单元统一接口 `run(context)`；`O_Workflow` 只认它。
- **包装器**（`orchestrate/component-wrappers.h`）：
  - `RunGenerate` 包 `OffspringGenerator`（内部用 topology+strategy+repair）。
  - `RunEvaluate` 包 `Evaluator`。
  - `RunSelect` 包 `EnvirSelect`，`run()` 末尾 **`offspring->clear()`**（所以 offspring 在"下一次 RunSelect 前"跨段累积）。
- **多段 workflow**：多个 `RunGenerate` 依配置顺序执行，offspring 累积，直到某个 `RunSelect` 归并并清空。分段点 = 后段生成是否依赖前段的评估/选择结果。
  - GA：交叉段 `generation()` + 变异段 `continueGraph()`+`generation(true)`（原地串联，见 `tutorial/2.subpopulation.cpp`）。
  - 免疫：两组「生成+评估+选择」（克隆选择 + 强制换血），见 `tutorial`/config-generate 的 immune。

> 关键不变量：`Individual` 全程守恒（选择用 swap 而非 new/delete）；offspring 缓冲只增不减（每代 clear 复用）。

## 4. 装配流程：从配置到 Optimizer

```
ConfigBuilder(fluent)                       用户写的
   │ .workflow(...)/.subpopulation(...)/.name/.manager...
   ▼
FullConfig { workflows[] + OptimizerConfig } 有序组件清单(configure-list.h)
   │
   ├─ buildOptimizer():
   │    for wf in workflows: _builder.registerWorkflow(wf)   // 注册各 workflow
   │    _builder.buildOptimizer(cfg)
   ▼
OptimizerBuilder                             装配器(orchestrate/optimizer-builder.h)
   │  ① AssertMatcher.validate(workflow)   // 装配期兼容校验,不兼容抛(v1.4.8 删 individual_type 形参)
   │  ② 按 config 顺序,经 Registry<Base>::create(tag,para) 造各组件
   │  ③ 组装 O_Workflow → Subpopulation → SubpopulationManager → Population → Optimizer
   ▼
Optimizer                                    可 setProblem + exe
```

- **`FullConfig` / `configure-list.h`**：`WorkflowConfig`（有序 `components` 表）+ `OptimizerConfig`（名/终止/协作/档案/子群清单）。所有算子以 `ComponentConfig{type, tag, para}` 记录，顺序即执行顺序。
- **`AssertMatcher`**（`config/assert-matcher.h`）：沿 workflow 累积各组件 `postAssert`（"已提供的上下文"），逐组件核对 `preAssert`（"需求"）。装配期即报不兼容（如拓扑 objects 不足；个体特性需求由 `featureDemands` 声明、装配期推断供给，不再校验个体类型）。见 算子组件模型.md。
- **`Registry<Base>`**：每类组件一张自注册表；`create(tag, para)` 按名造实例。新增组件 = 一个文件 + 一行 `ECFLOW_REGISTER`，装配器/配置层零改动。详见 [21](21-开发-内部组件.md)。
- **序列化**：`FullConfig ⇄ 文本(config-codec.h)/JSON(config-codec-json.h)`，可存盘复用。

## 5. 一图总览（问题 ⊕ 优化器）

```
用户: 定义 Problem ──compile()──► ProblemHandle ──┐
                                                  │ opt.setProblem()
用户: ConfigBuilder ──buildOptimizer()──► Optimizer ┘
                                                  │ opt.exe(seed)
                                                  ▼
   每轮: Population→Subpopulation→O_Workflow 顺跑[生成→评估→选择]
         · 生成器用 topology+strategy 造子代(消费 ProblemHandle 的 evaluate/greedy/feasible…)
         · terminator 命中(FES/收敛/时间)则停; archive 保全局最优
                                                  ▼
   opt.getBest(best, size)
```
